# 03 — Project structure

> Last updated: 2026-08-16

## The monorepo

```
Customer Panel/
├── package.json            # workspace root — scripts only, zero app code
├── package-lock.json       # the single lockfile for both apps
├── node_modules/           # hoisted; neither app has its own
├── .gitignore              # covers both workspaces
├── README.md               # quick start
├── AGENTS.md               # working agreement, loaded by every agent session
├── CLAUDE.md               # imports AGENTS.md
├── docs/                   # you are here
├── frontend/               # @customer-panel/frontend — Next.js
└── backend/                # @customer-panel/backend  — NestJS
```

Dependencies are declared per workspace and installed once at the root. Run `npm install` from the root; never inside `frontend/` or `backend/`.

Note the deliberate symmetry: the two `features/*/` trees differ only where the runtime forces them to — `presentation/views` vs. `presentation/controllers`, and a plain container vs. a Nest module.

## Where does this file go?

| What you are writing                                    | Where it goes                                                        |
| -------------------------------------------------------- | --------------------------------------------------------------------- |
| A business rule that is true regardless of UI or storage  | `features/<name>/domain/entities/`                                     |
| An interface describing data the feature needs            | `features/<name>/domain/repositories/` (a port)                        |
| A step the user or client can trigger                     | `features/<name>/application/use-cases/`                               |
| The shape sent to a component or over the wire            | `features/<name>/application/dto/`                                     |
| Code that calls an API, a database, or the file system    | `features/<name>/infrastructure/repositories/`                         |
| The wiring of a port to an implementation                 | `features/<name>/infrastructure/` (the composition root)               |
| A React component for one feature                         | `features/<name>/presentation/components/`                             |
| A React component two features both need                  | `frontend/src/shared/ui/`                                              |
| A controller / route handler                              | `features/<name>/presentation/controllers/`                            |
| A helper every feature may use, with no framework in it    | `core/`                                                                |
| A helper every feature may use, that touches the framework | `shared/`                                                              |
| A page or route                                           | `frontend/src/app/…/page.tsx` — three lines, rendering a feature view  |
| A unit test                                               | Next to the file under test, as `*.spec.ts`                            |
| An HTTP-level test                                        | `backend/test/*.e2e-spec.ts`                                           |

## Rules of thumb

- **Nothing business-related in `src/app/`.** Route files render a feature view and pass route params. If a route file grows past a handful of lines, the logic belongs in a feature.
- **A feature owns its whole vertical.** If a change touches only one product concern, it should touch only one folder under `features/`.
- **Reach for `shared/` only on the second use.** Two features actually needing the same thing is the trigger; anticipating that they might is not.
- **`core/` stays tiny.** It is for primitives every feature uses. If something in `core/` is used by one feature, it belongs in that feature.
